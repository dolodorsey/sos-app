# Preserve payout connections during lookup failures

A failed Stripe account lookup previously cleared the saved account ID and reset payout verification. The handler now returns 503 with verification_unavailable and retains the saved connection without database writes or an automatic retry. No connected/disconnected or payout-ready claim is made on this failure path. This includes 404: the current credential context alone cannot establish that the saved account should be erased.

Run `node tests/hero-payout-connection.test.mjs` (Node 22.13+). Eight actual-handler VM cases cover HTTP 503/429/401/404, network failure, successful status, authenticated creation metadata, and authentication rejection. Auth/database/Stripe are mocked; zero external requests or real accounts. The prior source fails the no-write failure regression.

This source change is pending independent review and deployment. Successful-path profile write errors/recompute errors, metadata and test/live mode verification, concurrency and atomic webhook integration remain separate unresolved work. The local database reconciliation prototypes are not included or deployed by this change. No authorization, money movement, account creation policy, dispatch or overall verification criteria changed.

November 1 caller contract QA: `node tests/hero-payout-caller.test.mjs` passes eight scenarios across the actual extracted mobility and readiness caller functions and request helpers. Both propagate the 503 message, release busy state, avoid success/navigation/reload and automatic retry on failure, preserve the existing payout state by not replacing it, and allow an explicit retry to follow a successful onboarding URL. Network and empty-error responses also release busy state. Session propagation and onboard payload are checked with synthetic credentials. Fetch and state setters are mocked; this is not React rendering, browser validation, production invocation or independent business QA. Application source is unchanged by this test addition.

November 2 persistence guard: profile update errors, verification-check write errors and verification recompute errors now return 503 without payout-ready or onboarding claims. Profile failure stops before writing the verification check; check failure stops before recompute. The unconnected status branch also handles persistence failure. Five actual-handler mocked regression scenarios pass via `node tests/hero-payout-persistence.test.mjs`; prior source returned 200/payout_ready=true for profile and recompute failures. This guards the response, not transaction atomicity: earlier successful writes can persist when a later operation fails. Existing connection-preservation and caller tests must remain passing. This change is pending review/deployment; no live accounts, payments or verification decisions were changed.

November 2 action validation: unsupported actions formerly reached Stripe/profile/check/recompute before rejection; an unconnected profile even returned 200 after a verification write. The handler now rejects malformed/non-object JSON and non-string/unsupported action values with 400 before Stripe or verification writes. Omitted action still defaults to status; explicit status/onboard remain accepted. `node tests/hero-payout-action.test.mjs` passes 25 mocked actual-handler scenarios (both connected/unconnected), alongside 21 affected persistence/connection/caller checks. Existing callers send explicit supported strings. Authentication/profile reads and a possible runtime-secret read remain before body validation; this change does not broaden access or make persistence atomic. No deployment or real account changes.
